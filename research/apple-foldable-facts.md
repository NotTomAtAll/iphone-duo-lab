# Apple foldable iPhone ("iPhone Duo"): grounded fact sheet

Researched 2026-10-20. Verified: an Apple source says it. Secondary: only non-Apple sources say it. Unverified: no reliable source found. Device availability date per Apple: October 23, 2026.

## Facts

| # | Fact | Answer | Confidence | Source |
|---|------|--------|------------|--------|
| 1a | Name | Apple calls the device **iPhone Duo**, "a foldable phone, with a compact outer display and a large inner display." Each display has a front camera. The inner camera sits behind the display and stays hidden until active. | verified | [Preparing your app for iPhone Duo](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo) |
| 1b | Pose vocabulary | The HIG says "poses", not postures: closed, partially folded "like a book", set on a surface (laptop-like), standing on its edges, fully open. The hinge API reports `.closed`, `.partiallyOpen`, `.fullyOpen`. The simulator buttons are Closed / Partially Open / Open. | verified | [HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo); [Tech talk 111464](https://developer.apple.com/videos/play/tech-talks/111464/) |
| 2a | Size classes, outer display | Compact width. Portrait is compact width with regular height. Landscape is compact in both. It behaves like other iPhones. | verified | [Tech talk 111461 "Prepare your app"](https://developer.apple.com/videos/play/tech-talks/111461/) |
| 2b | Size classes, inner display | **Regular width and regular height in both orientations**, so it is an iPad-like regular environment, not a landscape iPhone. The HIG says to design for two classes: compact on the outer display, regular on the inner. | verified | [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/); [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) |
| 2c | Aspect ratio of the outer display | The outer display is "wider and shorter than the display on other iPhone devices." That is why the system moves bars to the side. | verified | [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) |
| 2d | Point sizes (simulator) | Outer: 466×678 pt (1398×2034 px @3x). Inner: 669×951 pt (2007×2853 px @3x), landscape-native panel. Measured safe area on the closed outer display with the 27.1 SDK: top 82, bottom 34, trailing 84 pt. | secondary | [blakecrosley.com Xcode 27.1 Duo sim](https://blakecrosley.com/blog/xcode-27-1-beta-iphone-duo-simulator) |
| 2e | Orientation lock on the inner display | "The inner display **doesn't honor your supported interface orientations**… avoid checking interface orientation for layout decisions. Use size classes instead." The outer display honors them. | verified | [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/) |
| 2f | Portrait-only app with UIRequiresFullScreen on the inner display | Forum reports say orientations are honored only when `UIRequiresFullScreen` is set, and then the app is **scaled** rather than resized. I could not open the Apple forum thread to confirm (404). | secondary | [Apple forums 848598 (via search)](https://developer.apple.com/forums/thread/848598); [adapty.io](https://adapty.io/blog/adapt-your-ios-app-to-iphone-duo/) |
| 2g | `UIRequiresFullScreen` | "iPhone Duo will continue to honor the UIRequiresFullScreen key, but your app will still resize when someone opens or closes" it. With the iOS 27 SDK, the key no longer opts out of resizing. Instead the scene resizes **discretely**: it moves to a `UIScreen` of exactly the new size. The key is deprecated (since iPadOS 26) and will be ignored later. `UIRequiresFullScreenIgnoredStartingWithVersion` controls back-deploy. | verified | [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/); [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key) |
| 2h | Launch screen | Starting in iOS 27, App Store submission requires a launch screen (`UILaunchScreen`/`UILaunchStoryboardName`). No foldable-specific Info.plist key exists (none found). | verified | [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key) |
| 2j | Apps on older SDKs | iOS 26 SDK or earlier: the app runs but "doesn't extend under the status bar and camera." When closed it uses the space left of the status bar. When open it keeps a familiar size and aspect ratio, which secondary sources call letterboxed. iOS 27 SDK: the app fills most of the inner display but avoids the status bar. **iOS 27.1 SDK**: edge to edge, with vertical bars below the status bar. | verified (letterbox wording: secondary) | [Prepare page](https://developer.apple.com/iphone-duo/prepare/); [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/); [dev.to](https://dev.to/arshtechpro/iphone-duo-for-ios-developers-what-actually-changes-in-your-swift-code-5gc5) |
| 3a | Reserved regions | SwiftUI: `GeometryProxy.reservedRegions(kind:options:layoutDirectionBehavior:)` returns `[ReservedRegion]`. UIKit: `UIView.reservedRegions(kind:options:)` returns `[UIView.ReservedRegion]`. Kinds: `.division` for the fold, which is active only when partially open and has zero width when flat, and `.occlusion` for cameras. The outer camera always occludes. The inner camera occludes only when active. Use `.includeInactive` to get inactive regions. | verified | [Preparing doc](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo); [Tech talk 111463](https://developer.apple.com/videos/play/tech-talks/111463/) |
| 3b | Arrangement views | `ArrangementView` (SwiftUI) and `UIArrangementViewController` (UIKit) take a primary and a secondary view. Styles are `.split`, which splits along the longer axis, and `.overlay`, which stacks when there is no division and puts the views on either side of the fold when partially open. Axes can be restricted. Don't put one inside a NavigationSplitView, List or ScrollView. | verified | [Preparing doc](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo) |
| 3c | Vertical bars API | Opt in by rebuilding with the latest SDK and using system containers (NavigationStack/NavigationSplitView with `.toolbar`, or UINavigationController/UITabBarController). Custom `UIToolbar`/`UINavigationBar`/`UITabBar` bars are not converted. Opt out with `toolbarVerticalBehavior(.disabled)` or `preferredVerticalBarBehavior = .disabled`. Detect with `toolbarVerticalEdge` / `traitCollection.verticalBarEdge`. Per-item controls: `axisBehavior`, `visibilityPriority`, `ToolbarOverflowMenu` / `additionalOverflowItems`. | verified | [Preparing doc](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo); [Tech talk 111462](https://developer.apple.com/videos/play/tech-talks/111462/) |
| 3d | Hinge API | SwiftUI: `onHingeChange` gives the previous and current context. UIKit: `UIHingeInteraction`. `context.hinge` is nil on devices without a hinge. It has `status` (`.closed/.partiallyOpen/.fullyOpen`) and a continuous `angle`. Apple says to use it for effects and interactions, and to use arrangement and region APIs for layout. | verified | [Tech talk 111464](https://developer.apple.com/videos/play/tech-talks/111464/) |
| 3e | Scene and state continuity | Opening, closing or rotating the device moves "content… between displays". The app resizes and does not relaunch. The HIG asks for the same state and functionality on both displays. A scene accessory (`CameraCaptureAccessory`) can show content on the outer display while the app runs on the inner one. New windows cannot be created on the outer display. | verified | [Preparing doc](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo); [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo); [Tech talk 111464](https://developer.apple.com/videos/play/tech-talks/111464/) |
| 3f | Screen and orientation APIs to drop | Stop using `UIScreen.main` (it's ambiguous with two displays and will be deprecated). Use `window.windowScene.screen`, view or window bounds, and `traitCollection.displayScale`. Remove `UIDevice.orientation`, `statusBarOrientation`, `interfaceOrientation`, idiom checks, "regular means iPad" assumptions and hard-coded heights. | verified | [Prepare page](https://developer.apple.com/iphone-duo/prepare/); [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key) |
| 3g | Safe areas | Safe areas are **asymmetric**: vertical bars can be on the left or right. Don't compute width as `bounds.width - left*2`. Use `bounds.inset(by: safeAreaInsets)`. | verified | [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/); [Preparing doc](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo) |
| 4a | Adaptation strategy | Don't design per pose. Use size classes, layout margins and safe areas, and system containers (NavigationSplitView/UISplitViewController, TabView, sheets). Avoid fixed widths and breakpoints. The inner display can show an extra hierarchy level. `.defaultTabBarPlacement(.sidebar)` opts into a sidebar. | verified | [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo); [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/) |
| 4b | Letterboxing guidance | The HIG mentions letterboxing only for games: "Prefer changing the aspect ratio over letterboxing or pillarboxing." Games may lock orientation but must still fill the screen. I found no letterbox option for non-game apps. | verified | [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) |
| 4c | Portrait-only apps | Apple does not use the words "add landscape". It does say the inner display ignores supported orientations (2e) and that TN3192 expects "supports all interface orientations" for resizable scenes. In practice, a portrait-only app has to lay out at landscape-shaped regular sizes. | verified (inference noted) | [Tech talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/); [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key) |
| 4d | App Store expectations | Submitting Duo screenshots earns an "optimized" badge on the product page. **From April 2027, every submission must include iPhone Duo screenshots.** Apps must behave "across all poses and orientations." I found no App Review rule that rejects apps which aren't adapted. | verified (rejection rule: unverified) | [Apple news Oct 5 2026](https://developer.apple.com/news/?id=kkphp5qo) |
| 5a | Changing pose in the simulator | Requires Xcode 27.1. In Device Hub, the controls under the bezel are Closed (right of Rotate Right), Partially Open (middle) and Open (far right). Option-drag the slider below the bezel to set any angle. Rotation is via the rotate button or Controls > Rotate Left/Right. I found no fold keyboard shortcut. | verified (shortcut: unverified) | [Interacting with your app in Device Hub](https://developer.apple.com/documentation/xcode/interacting-with-your-app-in-device-hub) |
| 5b | simctl/devicectl | `simctl` has no pose, fold or hinge command, and `devicectl` has no hinge readback. Community tools (duoctl, foldctl) drive Device Hub through private APIs. | secondary | [Maestro #3617](https://github.com/mobile-dev-inc/maestro/issues/3617); [iphone-duo-simulator-skill](https://github.com/WhitenWhiten/iphone-duo-simulator-skill) |
| 5c | Simulator capture and automation | Inner display screenshot: `simctl io <udid> screenshot --display=primary-1`. Outer display: `--display=primary`. Xcode's device-interaction tools see only the outer display while the device is closed. `simctl io … screenConfig` crash-loops SpringBoard. | secondary | [blakecrosley.com](https://blakecrosley.com/blog/xcode-27-1-beta-iphone-duo-simulator); [iphone-duo-simulator-skill](https://github.com/WhitenWhiten/iphone-duo-simulator-skill) |
| 5d | Other ways to test | iOS resizable simulator in Device Hub, iPhone Mirroring on macOS 27, and the Xcode 27.1 "App Resizability" agent skill ("get my app ready for iPhone Duo"). | verified | [Prepare page](https://developer.apple.com/iphone-duo/prepare/) |
| 6a | HIG: bars | Toolbars, tab bars and navigation controls move to the **side** on the outer display and on the inner display in landscape. The **inner display in portrait keeps horizontal bars**. Top of the vertical bar: Back/Close, then the prominent action (Done). Overflow goes bottom to top. Give items both a symbol and a title. Text-only items stay horizontal. In Split View, each app puts its controls on its outer edge. | verified | [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) |
| 6b | HIG: fold and touch targets | Keep interactive elements out of the curve. Scrolling content may cross it. System sheets, alerts, menus and toolbar buttons move aside automatically. Prefer even grid columns and small adjustments. Apple gives no Duo-specific touch-target size, so the standard 44 pt still applies. | verified | [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo); [Tech talk 111466](https://developer.apple.com/videos/play/tech-talks/111466/) |
| 6c | HIG: continuity | "Keep functionality and the state of elements the same between displays." "Don't limit functionality to one pose." People open and close the device often. | verified | [HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo); [Tech talk 111466](https://developer.apple.com/videos/play/tech-talks/111466/) |

## Implications for a portrait-only iPhone app

1. **Portrait-only does not protect the app on the inner display.** Apple says the inner display ignores supported orientations. The window is regular×regular and near-square to landscape-shaped. Tall, narrow layouts get stretched there.
2. **Not rebuilding leaves the app in a compatibility presentation.** It keeps its old size, effectively letterboxed. That works short term, but Duo screenshots become mandatory in April 2027.
3. **`UIRequiresFullScreen` doesn't work as an escape hatch.** With the iOS 27 SDK it only changes resizing from live to discrete. The key is deprecated. Forum reports say scaling happens on the inner display, but treat that as unconfirmed.
4. **Rebuilding with the 27.1 SDK turns on vertical side bars on the outer display.** The safe areas become asymmetric. Custom bars and hard-coded symmetric insets break first.
5. **Minimum viable adaptation:** drive layout from size classes and container bounds, not from `UIScreen.main`, orientation or idiom. Let compact layouts stretch, capped at a readable width. Use NavigationSplitView or a sidebar TabView where a second level helps. Respect each safe-area edge separately. Keep controls out of the fold. Preserve state, because opening and closing the device resizes the app live; it doesn't relaunch.
6. **Testing:** changing pose in Device Hub is manual (no `simctl` pose command). Capture the inner display with `--display=primary-1`.
